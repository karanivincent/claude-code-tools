Spike first · two hours, one small page

Before building anything, test the ideas we are least sure of on one small page that already exists: the Settings Members section (live on staging, design already rendered). It has names, roles and emails to get right, and states that save. We add one calling-hours state to test the clock. Nothing gets built; we only test the pipeline around the page.

Part 2 · The workstreams

Each one: what goes wrong today, what changes, where, how it's tested, and what it saves.

W1The design pictures are rightsaves 40 min to 1.3 h

What goes wrong

  • Some designs keep their states in a table and pick one with a text prop. The renderer never finds those states, so they render as the default screen. Settings: 40 states fixed by hand. Rounds: about 125 states showed Home. (The plain "preset sets props" part was fixed in 0.13.4.)
  • Exports sometimes include a duplicate _bundle_src.dc.html, and intake refuses them. Both runs removed it by hand.
  • Phone views drawn inside an iframe can't be read.

What changes

  • The renderer finds preset tables and makes one state per entry, the way we did by hand.
  • Intake ignores the duplicate file and says so.
  • Phone states always come from --width phone; the renderer warns when a page is mostly an iframe.
  • A warning when a prop name clashes with a state name (the Rounds screen mix-up), and the stale help text is fixed.

Where

lib/design/claude-dc.mjs, lib/design/render.mjs, adapters/design/claude-design.mjs, lib/commands/design-render.mjs, the extractor brief.

Proof

The Settings export renders its 40 named states with no hand edits.

W2The page loads before we photograph itsaves about 1 h when a page breaks

What goes wrong

  • The shoot checks only the site's front page. A page returning errors is shot anyway: Rounds waited out 206 timeouts; Settings shot twice against a broken page (70 min).
  • A broken shoot still uses up a round number.
  • The builder reports done without opening the page.

What changes

  • A new delivery smoke opens every page of the run, signed in, at each width. It stops at the first server error, error overlay, or loading skeleton still showing after 10 s.
  • The shoot runs smoke first. A failure after the shoot deletes that round, so the number is reused.
  • Builder and fixer must pass smoke before they report done.

Where

New lib/commands/smoke.mjs; lib/commands/shoot.mjs, lib/picture/rounds.mjs, the builder and fixer briefs.

Proof

Replaying the Settings crash stops in seconds, not after 75 minutes.

W3Right data every timesaves about 1.5 h, and honest round counts

What goes wrong

ProblemEvidence in 0.14.0
Test data is guessed from picturesThe design's text is saved for every state, but the agent writing test data is never given it
The design shows things the product doesn't storeEvery gap is assumed fixable by re-seeding, so the run can never finish green (Settings: 28 items)
Saves leak into later statesRe-seeding happens between widths, not between states. One Settings world held 22 states, 6 of which save
Old rows stay behindRefresh only cleans tables the world still seeds
Values the code rejects pass the checkThe app's own rules are never checked (Rounds: mode: "manual" crashed the page)
New tables with no guardOnly a warning; seeding stops later
The clockNothing makes time-based states true when the picture is taken
Data gaps go nowhereA round with only data gaps says "ship" while the run stays red

What changes, in the order it runs

  1. Trace. At map time, every piece of data the design shows is labelled: a table column, a computed value, a fixed word, or no source.
  2. One list for you (D6). Every "no source" item and every guard to approve arrive in one message before the build. For each: build it, drop it, or send it back to the design. Decided items stop counting as problems.
  3. Test data uses the design's own values, written by a command (D13). delivery seed --from-trace turns the trace into world rows: same names, counts, statuses and relative dates, so the live page shows what the design shows. Any agent that needs different data asks with delivery seed --need instead of editing world files, and the command validates, applies and reports back in one line. This keeps seeding out of the agents' context. A small seed agent is dispatched only for what the command can't infer, and it sees one state's trace, not the whole map.
  4. Check before writing. Columns and types against the database types; data fields against the app's own validation rules, through a small script in the Telitask repo.
  5. Guards (D5). A table with no guard stops seeding. The mapper drafts the guard or an intercept; you approve it once, in the list above.
  6. Isolation (D3). A clean re-seed before every state that saves, and refresh removes any row not in the plan, in every table.
  7. Time (D4). Clock-sensitive states must use times relative to the shoot; a refresh runs just before shooting; the browser uses the organisation's time zone.
  8. Check the data before any reviewer looks. The shoot saves each page's text. A new delivery datacheck compares it with the traced values. A miss is fixed and re-shot automatically before review. Generated text (an AI summary) is checked by shape only. It's a text comparison: seconds, no tokens.

Where

Mapper and seed-writer briefs; lib/picture/map.mjs, lib/seed/*, lib/picture/shoot.mjs, lib/design/render.mjs, new lib/commands/datacheck.mjs, lib/picture/review.mjs, lib/picture/next.mjs, lib/run/ready-compute.mjs. In the Telitask repo: one validation script.

Proof

Replay Settings round 2: its 39 data gaps are fixed before review, or decided before the build.

W4Rounds without a fixed capno leftover-bug list

What goes wrong

Three rounds is a fixed number in the code, and the two places that check it count differently. After round 3, real bugs go to you as a list.

What changes

  • Keep going while the real-bug count falls. Stop at zero.
  • Stop after two rounds in a row with no fall, and send only the stuck items, each with why it didn't move. Ceiling: 8 rounds.
  • Both checks share one rule; a voided round never counts.

Where

lib/picture/next.mjs, lib/run/ready-compute.mjs, tunables.json, the picture-build skill.

W5Cheaper late rounds1.5 h → 20 to 30 min per late round

What changes

  • Re-shoot only items that didn't match, plus matching items whose page files changed. When unsure, shoot.
  • A matching item whose picture changed goes to a sample, one per screen group. If the sample finds a problem, the whole group is reviewed.
  • The last round before shipping reviews every changed item, so nothing ships unreviewed.

Where

lib/picture/shoot.mjs, lib/picture/review.mjs, lib/picture/map.mjs, the mapper brief.

W6Faster shoots35 min → about 10 to 12 min per shoot

What changes

  • Shoot against a production build; the dev server stays for the builder. A failed build stops the shoot.
  • Two browsers at once, each on a different world.
  • Fixed pauses and timeouts become settings; the click timeout after load drops from 8 s to 3 s.

Where

lib/picture/shoot.mjs, lib/commands/shoot.mjs, lib/capture/slots.mjs, tunables.json, the Telitask profile.

W7Better reviewsabout 1 h in wrong fixes and false findings

What goes wrong

  • Reviewers disagreed between rounds on the phone menus, so one fix went the wrong way.
  • The phone crop hides short bottom sheets and cuts the phone header on the live picture only: 13 false findings in Settings round 4.
  • The shoot's facts file is 500 KB, too big for reviewers to read.

What changes

  • Before round 1, one agent writes the reviewer guidance from the design: phone patterns, fixture names, rules that override the picture.
  • The crop hides only the real tab bar and crops both pictures the same way.
  • Reviewers get a short facts file per item, including the text differences from W3.
W8Shipping checksabout 1.5 h, and no silent data loss on staging

What goes wrong

  • Two runs redefined the same database function, and one silently dropped the other's tables on staging.
  • Retired test ids only surfaced at push time, which needed a prep PR and a wait for you.
  • Land missed a silently failed Vercel build and didn't re-run staging E2E after the deploy.

What changes

  • At map time, list files another open run also changes, and say who to coordinate with.
  • The retired-test-id check runs at map time; skipped tests are ignored.
  • Land checks Vercel's status on the merge commit, then re-runs staging E2E once the deploy is live.
W9Scope and modelsabout 2.5 h on a large design
  • Above about 120 states, the run proposes screen groups; each becomes its own run. At most four agents at once.
  • The first builder gets one screen group per dispatch, so it stops running out of turns (Rounds: four times).
  • Models as in D11. The builder-at-medium trial is recorded in the ledger so the retro can compare it.

How we measure

The runs ledger already records each phase's minutes and each agent's model and cost. After the next two runs, compare with Settings and Rounds on wall time, cost per run, rounds thrown away, data faults caught before review, and real bugs left. A workstream that doesn't move its number gets reverted.

Not in this plan

  • Machines don't replace the picture reviewers. They check data, loading and crops; judging the look stays with agents.
  • No test clock inside the dashboard.
  • No automatic guard approvals. The safety file stays yours.

Risks

  • The trace adds 10 to 15 minutes of mapper work; round 1 pays it back.
  • Production-build shoots wait for a free heavy slot at busy times; the wait is logged.
  • Sampling can miss a regression; the full review before shipping catches it.
  • Generated text is checked by shape only, so a wrong AI summary still needs a reviewer.
