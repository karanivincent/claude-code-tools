# Decision rules for the plan

Every table here is what `delivery plan check` enforces or what the later gates assume. The
profile's `limits` hold the numbers (`maxCuts`, `overSizeHours`, `maxPropOrUnseedablePct`).

## Classes

| Class | Meaning | Default when | Needs |
|---|---|---|---|
| `keep` | same capability, same place, unchanged | an old capability the design also shows unchanged | owner, reach and markers when its kind is `route` or `control` |
| `change` | same capability, redesigned | an old capability the design redraws | owner, reach, markers |
| `new` | in the design only | a designed state with no old counterpart | owner, reach, markers |
| `migrate` | an old capability the design omits, kept somewhere sensible | **every** old capability the design leaves out (the design may simply predate it) | `migrateTo: { file, control }`, owner, reach, markers |
| `remove` | dropped on purpose | never a default | `reason` (`unused` or `product-rule`), a Tier 1 decision file, a Scope line |
| `adapt` | built, but differently from the design because the design breaks a product rule | see "Adapt" below | `adapt: { rule, designText, productText }`, owner, reach, markers |
| `cut` | a designed state not built now | never a default | `reason` with one cut code, `issue`, budget; a Scope line when `requested` |

Kept content is audited like designed content: every `keep`, `change` and `migrate` row of kind
`route` or `control` gets reach steps and markers, so it is captured and linted even with no
design picture to compare against.

## Reach classes

| Class | Meaning | Verified by |
|---|---|---|
| `seeded` | reachable on a seeded page by URL, clicks, typing, or controls whose effect is `none` or `free`; includes error states reached by an intercept answering `500` or timing out | the capture, markers checked |
| `action` | needs a metered or dialling action | a capture with an `intercept` when the action is one HTTP request answerable from a fixture built from the real response type; otherwise a component render test |
| `prop` | reachable only by component state no data can produce (a transient state, a prototype-only switch) | a component render test with fixture props |
| `unseedable` | cannot be produced safely even in a fixture world | code-read by the auditor with a reason code, plus a component render test wherever the component can render it |

`unseedable` reason codes, and no others: `needs-live-call`, `needs-carrier`, `needs-time`,
`needs-third-party`, `unsafe-to-seed`.

**Before `prop` or `unseedable`, in this order:**
1. Can a world produce it? Counts, allowances, "used up", "none yet", "many", old-shaped rows:
   all of these are rows. Seed them in `limits`, `empty`, `day-one` or `messy`.
2. Can an intercept answer it? One HTTP request with a fixture body, a `500`, a timeout.
3. Does a guard in the founder's safety file cover the risky predicate? Then it is `seeded`.
4. Only now `prop` or `unseedable`, with the reason code and `reach.test` naming the component
   test that asserts every marker.

`needs-time` means only the clock can produce it (a reminder that fires tomorrow). A number that
grows over time is data, not time.

Cap: `prop` plus `unseedable` may be at most `limits.maxPropOrUnseedablePct` (default 20%) of the
`build` states. Over the cap, add a world or an intercept. Every non-`seeded` state is listed in
the report with its class and reason.

## Cuts

Default for every designed state: build it. A cut needs exactly one of these codes:

| Code | Means |
|---|---|
| `money` | it spends money per use beyond an existing metered allowance, or needs a paid service |
| `dials` | building it means placing real calls or messages, or changing telephony |
| `production` | it needs a production change outside a normal release |
| `new-vendor` | it needs a vendor or an account the company does not have |
| `over-size` | a backend piece estimated at more than `limits.overSizeHours` builder-hours |

- **Budget**: at most `limits.maxCuts` cut features per run (a feature is a group of states the
  plan names). Over it, `plan check` fails and the plan must build instead. `plan check` counts
  cut features by their follow-up issue, so the cut rows of one feature share one issue.
- Every cut has a follow-up issue (filed by `delivery issues sync`, which writes its number into
  the row; unclaimed, so another lane may take it later).
- A row carrying `requested` (the founder asked for it in a design round) is cut only through a
  Scope line. The same holds for every `remove`.
- A cut state is not audited against the design; the cut itself is the visible decision.

## The Scope issue

One per run, labelled with the profile's `issues.scopeLabel`, at most five lines, generated by
`delivery scope post` from `plan.json` `scope[]`. Only three kinds of line go there:

1. `cut-requested`: cutting something he requested in a design round;
2. `remove`: removing a capability the product has shipped;
3. `adapt-behaviour`: an `adapt` that changes behaviour a customer sees (not wording).

Everything else is a Tier 1 decision file (the profile's `decisions.file` path), which reaches
him in the handover. A `scope[]` entry: `line` (`S<n>`), `rows`, `kind`, `text` (what and why, one
sentence), `default` (what happens if he does not reply), `appliesAtWave`, `reply: null`. Set the
row's `scopeLine` to the same `S<n>`. Shape of a line as the founder reads it:

```
S1 · Cut "<feature>" (<reason code>: <one clause>). Default: cut; follow-up #<issue>.
     Applies at wave 1 start. Reply "S1 build" to build it.
```

More than five lines means the plan is wrong, and `plan check` says so.

## Late changes

The first `delivery scope post` takes the Scope snapshot (every row's class). Later posts keep
it and only update the lines. After the snapshot:

- any row whose class changes is a late change: add its Scope line at once (`plan.json`
  `scope[]` and the row's `scopeLine`, then `delivery scope post`), and it leads the report and
  the PR body. Never `--resnapshot` to make a late change look early;
- a `requested` row cannot change class late at all without his reply: its line's default is
  `build`, the row keeps its class, and the state stays red until it is built or he answers
  "S<n> cut".

## Adapt

| The design... | Default |
|---|---|
| uses a word the profile bans | the product's word wins silently (Tier 0); M4 then expects the product text named in the row |
| shows behaviour the product forbids | `adapt` with the rule named; a Scope line only when changing the rule would make a better product |
| shows data the product does not have | a backend unit to add it, or a cut with `over-size`; never invented data |
| is older than the product | `migrate` |
| is incomplete (no loading, error, permission states) | the house empty, error and skeleton components, as `new` rows with `invented: true` |

An `adapt` row's `adapt.rule` is one of exactly these four: `banned-word`, `product-behaviour`,
`data-not-in-product`, `older-than-product`. `adapt.productText` is what M4 then expects on the
page. The auditor re-judges a sample of adapt rows.

Where the design lacks a day-one state, also write a design-round brief in the founder's format
at `docs/delivery/<feature>/intent/rounds/round-next.md`, with a pass checklist. The build never
waits for it.
